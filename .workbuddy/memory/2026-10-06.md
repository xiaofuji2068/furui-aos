## ⚠️ 环境坑：`git commit && git push` 用 `&&` 串联会静默丢推送

- **现象（连续两次）**：执行 `git add -A && git commit -m "..." && git push`，
  输出却是 `nothing to commit, working tree clean` + `ahead of origin/master by 1 commit`，
  推送没发生。
- **根因**：该 Bash 环境里命令会被**重放/重试**一次。第一次执行时 commit 成功（新提交已生成，
  且其 message 就是本次命令里的原文），第二次重放时因无变更而失败；`&&` 链条一断，
  后面的 `git push` 就被整体跳过。
  （排查确认：`.git/hooks/` 无任何非 sample 的 hook，也没有自动提交脚本 —— 是命令重放，不是 hook。）
- **对策（重要）**：
  1. **git 操作一律用 `;` 分隔，不要用 `&&`** —— 保证 push 一定执行；
  2. commit 与 push **分两条命令**跑，别串在一起；
  3. 见到 `nothing to commit` 先别当失败：立刻 `git log --oneline -3` 确认提交是否已生成，
     已生成就直接 push。
- **判断改动是否真丢**：`git show HEAD:<file> | grep -c <关键字>`（查 HEAD 版本）+
  `grep -c <关键字> <file>`（查工作区），两者都为 1 即改动完好。

## 意外发现：并发会话在同一仓库操作

- 现象：我 `Edit` README 后执行 `git add -A && git commit`，却收到 `nothing to commit, working tree clean` + `ahead of origin/master by 1 commit`。
- 真相：提交 `d6dbe54`（20:22:50）由**另一个会话/窗口**在我改动落盘后抢先提交了，我的 commit 因此无变更可提交（`&&` 链断在 commit 处，后续 echo 未执行，一度误以为改动丢失）。
- **教训**：多会话同时操作同一仓库时，`nothing to commit` 不等于改动丢失 —— 先用 `git log origin/master..HEAD` + `git show --stat HEAD` + `grep -c <关键字> README.md` 三者交叉确认，再决定是否重做。
- 判断改动是否真的在：`git show HEAD:README.md | grep -c "关键字"`（查 HEAD 版本）/ `grep -c`（查工作区）。
