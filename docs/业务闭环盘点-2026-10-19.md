# furui-aios 业务闭环盘点（2026-10-19）

> 盘点依据：仓库内 `docs/MATURITY-MATRIX.md`（2026-10-05 行为级 L0–L4 实测）+ 2026-10-18 对 Agent / 主线 / 连接器的代码实况核对。
> 视角：业务闭环（能不能拿来跑真实业务），不是工程清单。

---

## 0. 一句话定位

furui-aios 是一个 **AI 操作系统 / 中台**（借鉴 Palantir Ontology + AIP + Agents），**不是单点业务应用**。
因此"能干什么"要拆两层：**平台能力闭环**（地基）与 **业务场景闭环**（具体业务跑完一圈）。

当前成熟度（2026-10-05 矩阵）：9 分册 39 有效模块，**L3=11 / L2=16~17 / L1=6 / L0=5 / 外4**；L3 率约 28%，"能用"合计约 72%。
今日补完 CI 红修复后，回归面升到 **26 脚本 / 673 断言全绿**（含 `test_trace`），但 Trace/Watchdog 生产闭环仍待补。

## 1. 已经能闭环跑通的部分

| 闭环 | 等级 | 说明 |
| --- | --- | --- |
| **销售下降归因 → 审批建单**（唯一完整业务闭环） | ✅ 真闭环 | 读 ERP → SQL 算头号下滑客户 → 建销售任务 → L3 审批 → 人审 → 写 SalesTask → Receipt 留痕；`test_mainline` / `test_api_mainline` 断言全锁 |
| **知识治理闭环** | ✅ | 草稿 → 审核 → 发布，RAG 只检"已发布"，跨租户校验 + 审计 |
| **长程任务人机协作** | ✅ | mainline 状态机 + 审批联动（批准→Completed / 驳回→Returned） |
| **受控动作闸门** | ✅ | 四级门禁（Agent 白名单 / 用户权限 / 参数 / 审批级）+ ActionReceipt 留痕 |
| **发布交付** | ✅ | Release 状态机 draft→staging→production + 签名 + SBOM |
| **多租户数据隔离** | ✅ 实测 | 40 张表 RLS/FORCE，受限角色越权被拦 |

## 2. 平台底座扎实，但不是"业务"

本体数字孪生、Schema 演进、图探索、Outbox/Projector、模型多提供方纳管、审批规则——这些工程能力达标（L3/L2），但它们是"能力"，不是某个客户能直接用的业务流。

---

## 3. 不能闭环的关键缺口（业务视角，按致命程度）

1. **没有任何真实外部连接器** 🔴
   全仓数据来自本地 `erp_crm.db`（mock SQLite）+ 硬编码 KB + 内存数据源。所谓"销售闭环"是**跑在假数据上的真逻辑**。接真实 ERP/CRM/MES 的 REST/JDBC/Webhook 连接器一个都没有（分册 10 全系最弱）。
2. **"AI"部分默认是演示态** 🟡
   Agent 框架有真实 LLM 通道，但 `llm_enabled` 默认关（无 key 走 mock）；且销售分析核心是**确定性 SQL 算环比**，不是 LLM 推断。没填 key 时整套是确定性脚本演示。
3. **生产化三件套此前为空** 🟡
   CI（今日补自动化但**待远端验证转绿**）、Trace 链路 ID、Watchdog 守护进程尚未真正立起。
4. **数据操作系统整册最弱** 🔴
   同步调度、管道构建、数据血缘、真实连接器全无（10-03 / 10-04 / 10-05 均 L0）。
5. **低代码 / 应用运行时薄、无插件插槽、真实环境投递未通** 🟠
   发布状态机有了，但没有把版本真正推到客户环境的动作。

---

## 4. 一句话判断

> 这是一个**工程底盘达标、内部可用的 AI 中台原型 / 演示底座**：语义本体、Agent 编排、审批闸门、多租户隔离都真做出来了；但离"能卖给客户跑真实业务"，还差三块——**真实数据连接器、生产化（CI/Trace/Watchdog）、以及端到端真实数据闭环**。
