# 最小真实连接器设计（furui-aios · 路线图第 2 步）

> 目标：让"销售下降归因闭环"从 **mock 数据** 切到 **真实数据源**，且不改动已有的分析 / 审批 / 建单链路。
> 定位：落在图谱模块 **10-02 数据源与连接器**（当前 L1：catalog 有、真实协议连接器无）。
> 约束：遵循 `.ai/README.md`「改核心前先设计」——本文为设计稿，实现需二次确认。

---

## 1. 关键发现：读取路径已收敛，连接器的落点很干净

通过代码实况核对，销售闭环的全部数据读取都经过 `data_gateway.query()`（即 `tool_gateway` 里的 `gw_query`）：

- `mainline.py:40/360` 步骤 1 `query_erp_orders` → `tool_gateway._t_query_erp_orders` → `gw_query`（读 `erp_crm.db`）
- `mainline.py:43/437` 步骤 4 `analyze_sales_drop` → `tool_gateway._t_analyze_sales_drop`（`tool_gateway.py:126`）→ `gw_query` 跑 SQL
- `bootstrap.py:445/448` 工具种子 `query_erp_orders` / `analyze_sales_drop` 权限层不变

**结论**：`data_gateway.query()` 是 ERP/CRM 的唯一只读网关（只读闸门 `_assert_readonly` + 行数限制 `_apply_limit` + PII 脱敏 `_mask`），背后就是 `backend/data/erp_crm.db`（SQLite 投影）。
→ 连接器只需在「同步」时把真实数据**物化（materialize）进 `erp_crm.db`**，下游分析 / 审批 / 写 SalesTask 全部原样复用，零改动。

## 2. 设计方案

### 2.1 数据流（文字图）

```
真实 ERP/CRM（REST JSON）
        │  pull()  HTTP GET/POST + Bearer/APIKey
        ▼
┌──────────────────┐   mapping（字段映射）   ┌──────────────────────┐
│  RestJsonConnector│ ──────────────────────▶│  materialize()        │
└──────────────────┘                        │  写 orders/customers/ │
                                            │  products/sales_reps  │
                                            │  （幂等全量覆盖）       │
                                            └──────────┬───────────┘
                                                       ▼
                                            erp_crm.db（缓存投影，复用既有表结构）

```

### 2.3 改动既有（最小）

| 文件 | 改动 | 说明 |

### 2.4 安全性（对齐 60-03 / 60-04）

- `data_gateway._mask`（PII 脱敏）与只读闸门在真实数据上照样生效——连接器只负责"喂数据"，查询层天然安全。
- 认证密钥：当前 `secret_entries` 只存哈希（见 MATURITY-MATRIX 60-04），无法回明文。MVP 阶段连接器从**环境变量 `ERP_API_KEY`** 或数据源 config 内联读取；SecretRef 真正回明文作为后续升级（不阻塞本次）。
- 连线仅 `httpx` 出站到配置域名，不引入新依赖栈；失败隔离，不影响 mock 兜底。

## 4. 风险

| 风险 | 缓解 |
| --- | --- |
| 真实源字段与样例 schema 不一致 | `mapping` 做字段映射；materialize 失败即 error，不动 `erp_crm.db` 已有数据 |
| 大表全量覆盖锁表 / 慢 | MVP 走全量幂等；后续改增量 upsert + 临时表切换 |
| 密钥明文 config | 优先 env 变量；config 内联仅限开发态，生产走 SecretRef 升级 |
| 误伤现有测试 | 默认 mock 不变；测试只新增 `test_connector`，不动 26 个既有脚本 |

---

## 5. 验收标准

1. 不配置真实源时：行为与今日完全一致（mock，26 脚本 / 673 断言全绿）。
2. 配置一个真实 REST 源并 `POST /sync` 后：`erp_crm.db` 的 orders/customers 被真实数据覆盖；`query_erp_orders` 返回真实条数；`analyze_sales_drop` 在新的真实数据上仍能定位 `top_drop_customer` 并触发审批建单——**销售闭环在真数据上跑通**。
3. `test_connector.py` 封闭验证上述第 2 条（本地 http.server 提供 JSON fixture），纳入回归。

## 6. 不在本次范围（明确划界）

- 增量同步 / CDC / 流式（Kafka/MQTT）——后续 10-03/10-04。
- JDBC/MySQL/SAP 等多协议连接器——本次只做 **REST JSON** 一种，验证"接真实源"这条路通。
- 数据血缘 / 质量（10-05）——不做。
- SecretRef 回明文 + 密钥轮转（60-04 升级）——仅留接口位，不阻塞。
